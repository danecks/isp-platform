El sistema ya tiene:
- pizarrón operativo
- empleados
- asignación operativa base
- ficha del colaborador
- ficha del cliente
- agentes asignados por cliente
- historial de titularidad
- cobertura diaria
- segmentos de cobertura
- cierre diario
- RRHH
- pre-planilla

No quiero romper nada de lo existente.

Quiero mejorar el flujo del pizarrón operativo, porque es desde ahí, y especialmente desde la tablet, donde el personal de operaciones hace la mayoría de cambios reales.

## Objetivo
Que cuando operaciones haga un movimiento en el pizarrón, el sistema detecte el contexto del cambio y pregunte lo necesario en ese momento, para decidir si el movimiento es solo temporal o si debe cambiar la estructura base del sistema.

No quiero un flujo pesado, pero sí quiero que los cambios importantes queden bien decididos desde el pizarrón y se reflejen automáticamente en empleados, clientes y operación.

---

## 1. Contexto del problema
Ejemplo real:

- Un agente se reporta enfermo
- Su puesto queda descubierto
- Operaciones desde la tablet asigna a Daniel a ese puesto

En ese momento el sistema debe preguntar:

¿Daniel entra como relevo temporal o como nuevo titular del puesto?

Porque según esa decisión cambian varias cosas del sistema.

---

## 2. Pregunta obligatoria desde el pizarrón en ciertos casos
Cuando desde el pizarrón se asigne un colaborador a un puesto descubierto o a un puesto cuya cobertura implica una decisión estructural, el sistema debe mostrar una pregunta clara y rápida.

Texto sugerido:
¿Cómo deseas registrar esta asignación?
- Relevo temporal
- Nuevo titular del puesto

Esto debe pasar especialmente cuando:
- el colaborador viene del pool de disponibles
- el puesto tiene o tenía titular
- el movimiento puede cambiar la asignación base

---

## 3. Si el usuario elige “Relevo temporal”
El sistema debe:

- crear solo la cobertura diaria / segmento
- registrar el movimiento como relevo
- NO cambiar la asignación base del colaborador
- NO cambiar su cliente/sede/puesto titular
- NO cambiar los agentes asignados como titulares en la ficha del cliente
- mantener intacta la estructura base del puesto

---

## 4. Si el usuario elige “Nuevo titular del puesto”
El sistema debe:

- actualizar la asignación operativa base del colaborador
- convertirlo en titular del puesto
- actualizar su ficha del colaborador
- actualizar la ficha del cliente
- actualizar la sección de agentes asignados
- registrar el cambio en historial de titularidad
- registrar fecha efectiva y motivo si ya existe esa lógica

Si el puesto tenía un titular anterior, mantener el flujo ya existente:
- mover a disponibles
- mover a pool de relevos
- dejar sin asignación

---

## 5. Casos donde debe preguntar
Quiero que el sistema detecte y pregunte en situaciones como:

### A. Asignar a un puesto descubierto
Especialmente si el puesto tenía titular previo o si el colaborador viene del pool.

### B. Cubrir una ausencia prolongada
Ejemplo:
- enfermedad
- suspensión
- baja temporal
- incapacidad

En estos casos el sistema debe permitir decidir si se trata solo de cobertura temporal o de cambio estructural.

### C. Reemplazo operativo con impacto en el cliente
Si el cambio debe reflejarse en “agentes asignados” o en la ficha del cliente, el sistema debe pedir confirmación.

---

## 6. Casos donde NO debe preguntar
No quiero volver lento el pizarrón.

Por eso NO debe preguntar en:
- movimientos parciales de horas
- relevos cortos dentro del mismo día
- segmentación simple de cobertura
- cambios que claramente solo son operativos y temporales

En esos casos debe seguir siendo rápido.

---

## 7. Tablet / UX
Esto debe estar optimizado para uso rápido desde tablet.

Quiero:
- modal simple
- botones grandes
- flujo corto
- lenguaje claro

No formularios largos.

---

## 8. Consecuencias automáticas por módulo
Según la decisión tomada en el pizarrón, el sistema debe reflejar cambios automáticamente en:

### Si es temporal
- cobertura diaria
- segmentos
- operación del día

### Si es titular
- asignación operativa base
- ficha del colaborador
- ficha del cliente
- agentes asignados
- historial de titularidad

---

## 9. Integración futura
Dejar esta lógica preparada para que después también pueda alimentar:
- RRHH
- pre-planilla
- reportes
- historial operativo

Pero sin romper lo que ya existe.

## 11. Documentación
Explica claramente:
- en qué casos aparece la pregunta
- qué significa “relevo temporal”
- qué significa “nuevo titular”
- qué módulos se actualizan en cada caso
- cómo se mantiene rápido el flujo desde tablet

Muy importante:
quiero que el pizarrón operativo siga siendo rápido y usable desde tablet, pero que cuando un cambio afecte la estructura base del sistema, el usuario lo decida ahí mismo y el sistema actualice automáticamente empleados, cliente y asignaciones.
