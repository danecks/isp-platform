Actúa como un **auditor senior de seguridad de aplicaciones web** y revisa mi código actual de forma **crítica, técnica y práctica**.

Quiero que analices específicamente estos 3 módulos públicos, es decir, formularios a los que el usuario puede entrar **desde cualquier lugar en internet**:

1. **Solicitud de anticipo**
2. **Actualización de datos**
3. **Formulario de solicitud de empleo**

## Objetivo

Necesito que me digas **qué niveles de seguridad existen actualmente en el código**, qué controles sí están implementados, cuáles faltan, qué tan grave es cada hallazgo y qué riesgo real tenemos hoy.

## Contexto importante

### 1) Solicitud de anticipo

* Este módulo es especialmente sensible porque se trata de un **anticipo de sueldo** y el dinero puede llegar **directamente al colaborador**.
* En ese flujo puede existir lectura de DPI, OCR, validación contra base de datos, creación de solicitud y revisión/aprobación interna.
* Evalúa este módulo como un **flujo financiero sensible** con riesgo de fraude y suplantación.

### 2) Actualización de datos

* Este módulo también es **altamente sensible**, porque desde allí el usuario podría modificar información que impacta pagos, especialmente:

  * **cuentas bancarias**
  * datos personales
  * teléfonos
  * correos
  * direcciones
  * documentos
* Si un atacante logra cambiar la cuenta bancaria del colaborador, podría redirigir depósitos o pagos.
* Evalúa este módulo también como un **flujo financiero sensible** con alto riesgo de fraude, suplantación y secuestro de identidad.

### 3) Solicitud de empleo

* Este módulo también es público y puede recibir datos personales y archivos.
* Evalúa riesgos de abuso, spam, bots, fuga de datos y subida maliciosa de archivos.

## Supuestos de amenaza

Asume que estos 3 formularios públicos están expuestos a:

* bots
* spam
* fuerza bruta
* suplantación de identidad
* manipulación de requests
* enumeración de usuarios
* abuso de archivos subidos
* fuga de datos personales
* fraude

* modificación indebida de datos del colaborador

## Instrucciones de auditoría

* No me digas solo “parece seguro”.
* Quiero que inspecciones rutas, controllers, middlewares, validadores, APIs, auth, upload handlers, queries, configs y variables de entorno usadas en estos módulos.
* Si no encuentras algo, dilo claramente: **“no se encontró evidencia de…”**
* No asumas que una validación frontend protege el backend.
* Si detectas controles débiles, clasifícalos como débiles aunque existan.
* Si algo depende solo de Referer, dilo expresamente como **seguridad insuficiente**.
* Si OCR o foto de DPI se usan como prueba principal de identidad, dilo expresamente como **autenticación insuficiente para operación financiera**.
* Si el cambio de cuenta bancaria puede hacerse sin verificación reforzada, clasifícalo como **vulnerabilidad crítica**.
* Señala cualquier flujo que permita fraude por suplantación.
* Señala cualquier endpoint público que pueda ser automatizado o abusado.
* Señala cualquier respuesta de API que filtre demasiada información.
* Si encuentras buenas prácticas, repórtalas también.

## Criterio especial para anticipo y actualización de datos

Quiero que ambos módulos se evalúen como **flujos financieros sensibles**, no como formularios comunes, porque:

* uno puede terminar en desembolso directo al colaborador;
* el otro puede cambiar la cuenta bancaria a la que se deposita.

Por lo tanto, revisa si el código realmente está al nivel de una operación que puede afectar dinero real y datos sensibles.
